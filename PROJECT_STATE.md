# PanelOptimizer — состояние проекта

## Статус

Core-часть проекта завершена на текущем этапе. Все существующие тесты пройдены. Следующий этап — разработка UI в новом чате.

Последний подтверждённый этап: `PanelOptimizer.Calculate()` формирует полный результат расчёта, включая необходимое количество исходных панелей и план раскроя. Перед переходом к UI пользователь запустил весь набор тестов — всё успешно.

## Назначение проекта

PanelOptimizer рассчитывает производство клапанов из исходных панелей.

Типовой исходный материал: панель `6000 × 1200`.

Важная физическая модель:

- исходная панель имеет длину 6000 и высоту 1200;
- панель режется вдоль длины на заготовки;
- после раскроя заготовка поворачивается на 90°;
- поэтому `Height` исходной панели `1200` становится `Length` заготовки;
- ширина реза исходной панели становится `Height` заготовки;
- например, из `6000 × 1200` можно получить четыре заготовки `1280 × 1200` и остаток `880 × 1200`.

## Границы ответственности

Программа НЕ занимается:

- проверкой фактического наличия материала на складе;
- закупкой панелей;
- ожиданием поставки.

`PanelOptimizer` рассчитывает, сколько исходных панелей потребуется для заказа. Пользователь затем сравнивает это количество с фактическим складским остатком. Если материала недостаточно, закупки получают информацию о необходимом количестве.

Материал между разными заказами НЕ переходит. Но внутри одного заказа могут быть клапаны разной высоты и длины, поэтому остаток от панели может использоваться для другой позиции того же заказа.

## Основные правила материала

### Offcut

Физический остаток исходной панели не исчезает автоматически. Он сначала представлен как `PanelOffcut`.

`OffcutEvaluator` проверяет, подходит ли остаток хотя бы одной позиции текущего заказа.

- подходит → остаток превращается в `Blank` и может участвовать в производстве этого же заказа;
- не подходит ни одной позиции текущего заказа → `Waste`.

Например:

- заказ содержит клапаны высотой `1280` и `880` → остаток `880` можно использовать;
- заказ содержит только высоты `1200`, `1220`, `1280` → остаток `880` становится `Waste`.

Важно: даже `Waste` должен сохраняться в результате для статистики использования материала и отображения на схеме раскроя.

## Текущая архитектура Core

Основная цепочка:

```text
ValveOrder[]
    ↓
PanelOptimizer.Calculate()
    ↓
определение RequiredPanels
    ↓
PanelCutter
    ↓
PanelCutResult
    ├── Blanks
    └── Offcuts
    ↓
OrderMaterialPlanner
    ↓
Blanks + Waste
    ↓
MaterialPool
    ↓
ValvePlanner
    ↓
ValveAssemblyResult[]
```

### PanelCutter

`PanelCutter` режет исходную `Panel` и возвращает `PanelCutResult`.

`PanelCutResult` содержит:

- `Blanks` — полученные заготовки;
- `Offcuts` — физические остатки.

Старой модели `BlankCutter` больше нет. Она была удалена.

### PanelOffcut

Представляет физический остаток исходной панели.

Важно различать:

- `PanelOffcut` — материал;
- `PanelCutPlan.RemainingLength` — геометрическая информация для схемы раскроя.

`RemainingLength` из `PanelCutResult` был удалён, но он по-прежнему правильно существует в `PanelCutPlan`.

### OrderMaterialPlanner

Связывает результат раскроя с конкретным заказом.

Для каждого `Offcut`:

```text
usable → Blank
waste  → Waste
```

Если `Offcut` становится `Blank`, сохраняются его размеры и `SourcePanelPosition`; для нового `Blank` задаются `Tongue` / `Groove`.

### ValvePlanner

Отвечает за подбор материала из `MaterialPool` и сборку клапанов.

Важное ранее решённое правило: при сборке клапана из нескольких кусков последовательность заготовок имеет значение. Разрезанные части должны сохранять физическую последовательность. Остаток от разрезанной заготовки может быть началом следующего клапана.

Был реализован и проверен длинный цепочный сценарий, например для длины клапана `2700`:

```text
1: 1200 + 1200 + 300
2: 900  + 1200 + 600
3: 600  + 1200 + 900
4: 300  + 1200 + 1200
5: 1200 + 1200 + 300
```

### MaterialPool

Хранит доступные `Blank` текущего заказа.

Важно: при разрезании заготовки остаток должен сохранять правильную ориентацию и физическую последовательность.

### PanelCutPlan

Уже существует и предназначен для описания раскроя одной исходной панели:

```csharp
public class PanelCutPlan
{
    public int PanelIndex { get; init; }
    public int PanelLength { get; init; }
    public int PanelHeight { get; init; }
    public IReadOnlyList<Blank> Blanks { get; init; } = Array.Empty<Blank>();
    public int RemainingLength { get; init; }
}
```

### CuttingPlan

Содержит список `PanelCutPlan` для всех исходных панелей и предназначен, в том числе, для будущей визуализации раскроя.

### OptimizationResult

На текущем этапе содержит концептуально:

```text
RequiredPanels
CuttingPlan
Valves
Waste
```

То есть UI должен получить из Core:

- сколько исходных панелей требуется;
- схему раскроя каждой исходной панели;
- готовые клапаны и их состав;
- отходы.

## Что уже протестировано

Тестами покрыты:

- раскрой панели `6000 × 1200` на `1280`-заготовки;
- корректное создание `PanelOffcut` `880 × 1200`;
- использование подходящего offcut внутри текущего заказа;
- превращение неподходящего offcut в `Waste`;
- правильная ориентация заготовок;
- разрезание заготовок на части для клапана;
- использование остатков от резки заготовок;
- корректная последовательность частей при длинной цепочке клапанов;
- клапан из одного куска с `Cut` на обеих внешних сторонах;
- клапаны из нескольких кусков с обязательными `Tongue` / `Groove` на соединениях;
- расчёт количества исходных панелей;
- интеграционный pipeline от `PanelCutter` через `OrderMaterialPlanner` и `MaterialPool` до `ValvePlanner`;
- формирование `CuttingPlan` для исходных панелей.

Все тесты на момент передачи проекта пройдены.

## Важные принятые решения

1. Между заказами материал не переходит.
2. Внутри одного заказа можно использовать остаток для другой позиции заказа, если высота подходит.
3. Неподходящий остаток не удаляется — он становится `Waste` и участвует в статистике.
4. `Waste` должен быть доступен UI и для схемы раскроя, и для расчёта процента использования материала.
5. Закупки и склад не входят в Core.
6. `RequiredPanels` — расчётная потребность, а не количество панелей на складе.
7. Схема раскроя должна храниться в Core, а UI только визуализирует её.
8. Не следует создавать новые параллельные модели, если соответствующая модель уже существует (`PanelCutPlan`, `CuttingPlan` и т. п.).

## Следующий этап — UI

Работу над UI пользователь хочет продолжить в НОВОМ ЧАТЕ.

Первый UI должен использовать готовый `OptimizationResult`, не воспроизводя расчёты Core.

Предполагаемая структура интерфейса:

### Ввод заказа

Пользователь должен иметь возможность добавлять позиции заказа, например:

```text
Высота | Длина | Количество
1280   | 2700  | 5
880    | 1800  | 3
```

и запускать расчёт.

### Результат расчёта

Нужно показать минимум:

- требуемое количество исходных панелей;
- количество готовых клапанов;
- отходы;
- процент использования материала;
- схемы раскроя каждой исходной панели;
- состав каждого клапана.

### Визуализация раскроя

`CuttingPlan` уже содержит данные для построения горизонтальной схемы исходной панели:

```text
┌────────────────────────────────────────────────────────────┐
│ 1280 │ 1280 │ 1280 │ 1280 │             880              │
└────────────────────────────────────────────────────────────┘
  Blank  Blank  Blank  Blank             Offcut/Waste
```

UI не должен самостоятельно рассчитывать размеры — он получает их из `PanelCutPlan`.

### Статистика

Нужно будет определить точную формулу процента использования материала. Предварительная логика:

```text
использованный материал / площадь исходных панелей × 100%
```

При этом `Waste` должен отображаться отдельно, включая физические остатки вроде `880`, если они непригодны для текущего заказа.
